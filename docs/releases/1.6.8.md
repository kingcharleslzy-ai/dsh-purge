# 1.6.8 Windows real-machine install acceptance

Environment: genuine Windows 11 Pro, build 26300; official DSH Desktop 0.2.1-rc.2 Windows x64. The Authenticode signature on the installer and the app exe is valid, issued to DeepSeek. A separate test app directory, DSH_HOME, and user-data-dir were used, containing no user accounts, credentials, or existing business data.

## Problem found on the real machine

1.6.7's PowerShell entry ran the Desktop exe with the call operator. That exe is a GUI subsystem process, so PowerShell could return first and then run `finally` to delete the temporary script. Measured: the parent process returned success and the child later reported MODULE_NOT_FOUND. The ordinary Node console stand-in on the GitHub Windows runner could not cover this difference.

## Fix and regression

- Use Start-Process to wait for the process to finish, read the real ExitCode and UTF-8 stdout/stderr, and only then clean up the temporary directory.
- Windows native arguments are passed with full quoting rules, without shell command concatenation.
- Added a real GUI subsystem test program that reads the script late, covering success, argument passing, and non-zero exit; it runs on Windows PowerShell 5.1 and PowerShell 7. That program is only a regression stand-in, and real DSH install acceptance is recorded separately.

## Verified scope

- The official Desktop copy was actually started and confirmed to create a separate desktop profile; only the initialization stage is verified here, and this is not claimed as full UI acceptance. A plain CLI cannot create a reserved desktop profile, and hand-written configuration must not stand in for this step.
- The fixed PowerShell entry used the real Desktop Electron and its bundled CLI to complete SHA256 verification of the public release package, installation, snapshot, and rollback.
- Existing test prompts were preserved; after backing up and then editing the prompt, rolling back the plugin still kept the later content.
- The tests do not auto-apply host patches, do not restart the user's existing DSH, and do not change the existing image-generation service or network proxy.

Full Windows UI, account login, and all host patch functionality are not claimed as passing in this install acceptance. This record contains no host addresses, real usernames, account files, or private paths.

Addition: the same Windows 11 machine also installed through the native CLI using the marketplace Git source method (keeping supply-chain checks, selecting a public mirror at process level) and upgraded from that install to the 1.6.8 candidate package, with the current prompt unchanged. The missing-metadata error that issue #7's reporter saw did not reproduce here, and one success is not treated as covering all network/mirror environments.

[Three-platform and GUI process regression CI](https://github.com/kingcharleslzy-ai/dsh-purge/actions/runs/39097652231) passes fully. Real-machine acceptance and CI stand-in results are recorded separately.

Recheck after the formal release: on the same Windows 11 machine, the public v1.6.8 PowerShell entry completed SHA256 verification and a real Desktop install; PowerShell 7 also completed a dry-run. The public package was snapshotted and rolled back again, the current prompt was preserved, the default DSH_HOME was still not created, and the existing image-generation service kept running. The [release CI](https://github.com/kingcharleslzy-ai/dsh-purge/actions/runs/39097728324) and the marketplace release passed.
